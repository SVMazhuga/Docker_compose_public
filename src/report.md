Напишем Dockerfile для session service 

Разделим на два стейджа: 

- build - кеширование переменных, сборка бинарей
- runtime - сборка конечного docker-образа

![P1.3](./assets/P1.3.png)

Кратко о build stage:

- Указываем в `Build stage` в разделе `FROM` пометку AS `builder`, чтобы в `Runtime stage` сработала строка `COPY --from=builder`
- Сначала копируем редко изменяемые зависимости в верхние слои, потом то, что меняется часто

### 3.3 Docker Swarm

Зачем нужен `manager01`, `worker01`, `worker02`?

manager: 
- хранение состояния, 
- планировщик задач,
- распределитель нагрузки между воркерами
- упраление воркерами
- принимает команды от пользователя  

worker01/02: 
- запуск контейнеров
- выполнение команд manager'a
- отчитыватся о статусе 

`Docker Swarm` делает с машинами ровно то же, что `kubernetes` с подами - создаёт между ними `overlay сеть`. 

`Overlay сеть` - виртуальная сеть поверх физической. Итог - разные машшины в одной сети, будто бы в loopback. 

Как происходит инициализация:
- `docker swarm init --advertise-addr 192.168.56.10` 
таким образом мы сделаем сервер с этим адресом - менеджером

![P3.7](./assets/P3.7.png)

![P3.8](./assets/P3.8.png)

- После, с сервера-менеджера запросим токен для подключения воркера: `docker swarm join-token worker`

После, добавим каждого воркера. Взяв под контроль воркера, ввести команду:

### 3.5 Docker-stack

Теперь перейдём к модификации `docker-compose.yml`, приведению структуры проекта к потребной, а именно:

- вынесем `.env` файлы в отдельную папку `deploy` для удобства применения `env_file`
- Составим `docker-stack.yml` на основе `docker-compose.yml`

Начнём с `.env` файлов. 

В томе `manager01` лежат сервисы. При помощи `bash`-команды перекопируем в `~/deploy/env/` файлы с переименованием. 

`find ./services -name ".env" | while read f; do cp "$f" ~/deploy/env/"$(basename $(dirname "$f")).env"; done`

![P3.13](./assets/P3.13.png)

Вся модификация `.env`-файлов заключается в внесении в него `JAVA_OPTION_TOOL`, поля `POSTGRES_DB`

Пишем `docker-stack.yml`. Модифицируем `docker-compose.yml`, а именно:

- Убираем публичные порты (в оверлей сети не нужны, обращение напрямую к сервисам запрещено заданием)
- Убираем `depends_on` (не работает в `swarm`)
- Убираем `build` (уже есть образы)
- Указываем образы, загруженные в `Docker Hub`
- Монтируем `env_file`
- Указываем количество реплик в поле `deploy` (у нас всё по 1, можно было не делать)
- Меняем драйвер `bridge` на `overlay` в поле `networks`: `backend`: `driver`
- Добавляем `start_period` для `postgresql` , `rabbitmq` 10 и 30 секунд соответственно (а, что мешало сделать это раньше?!)
